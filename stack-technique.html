PARTIE 1 — LA STACK, ET POURQUOI

1. La décision de fond : un seul langage

TypeScript partout. Un seul langage pour le tracker, l'API, le site public et le tableau de bord. Une seule base de code, une seule compétence à recruter, un seul environnement.

Ce n'est pas une préférence de goût. C'est une question de friction : dans un projet naissant, chaque langage supplémentaire est un déploiement supplémentaire, un recruiting supplémentaire, et un endroit de plus où une erreur se cache.

CoucheChoixPourquoi celui-là
LangageTypeScript sur Node.js 22Les SDK officiels Meta et WhatsApp sont Node-first. Le mobile money est du HTTP et du JSON. Un seul langage pour toute l'équipe.
Back-endFastify + ZodLéger, rapide, fortement typé. La réception de webhooks est son cas d'usage principal.

2. Ce que je n'utiliserais pas

ÉcartéRaison
PHP / LaravelExcellent, mais ici tout le métier est du tracking asynchrone temps réel, et les SDK Meta sont Node-first. Si l'équipe est experte Laravel, ça se défend. Sinon, deux langages à maintenir.
Python / FastAPITrès bon, mais moins bon sur WhatsApp et sur le front. À réintroduire plus tard si tu fais de la recommandation ou de l'analyse comportementale.
GoTechniquement supérieur pour du trafic de clics. Mais tu gères quelques centaines de milliers de clics par jour au début, pas des millions. Go coûte du temps d'itération et un bassin de recrutement plus étroit.
MongoDBAucune raison de l'utiliser ici. PostgreSQL fait le travail et évite une deuxième base à opérer.
Next.js seul, sans back-end séparéAcceptable au démarrage. Mais le tracker doit vivre dans son propre service dès que le trafic monte : il est sensible à la latence et ne doit pas partager un runtime avec le catalogue.

3. Les compétences qui ne périment pas

C'est le vrai critère de durabilité, davantage que la technologie :

  • SQL. Aucun framework ne le remplace, et tes données d'attribution sont fondamentalement relationnelles : un clic appartient à un établissement, à une date.
  • La sémantique HTTP. Codes de statut, redirections, idempotence. Ta redirection serveur est ton cœur de métier.
  • L'idée de file d'attente. Découpler une action lente d'une requête utilisateur.

Une règle à retenir : n'ajoute une technologie que lorsqu'elle te débloque un problème que tu as réellement rencontré.

PARTIE 2 — LA BASE DE DONNÉES
db/schema.sql Rôle : définir les trois tables du projet et la vue qui produit le tableau de bord. C'est le seul endroit où vit la règle anti-fraude.

Trois idées structurent ce fichier :

  1. etablissements — l'offre, avec le vrai numéro WhatsApp du commerce.
  2. clics — la preuve, horodatée, écrite par le serveur uniquement.
  3. conversations — ce que le client déclare, filtré par code de référence.

Il n'y a pas de table reservations. On ne touche pas aux transactions : c'est ce qui élimine tout le risque financier du modèle.

Le point le plus important du fichier est l'index unique idx_clics_anti_fraude à la fin. Il interdit deux clics comptés pour le même établissement, le même visiteur, le même jour. Ce n'est pas du code applicatif qu'on peut contourner : c'est la base elle-même qui refuse la seconde ligne.

-- Schema de la base. C'est ici que tout se joue : chaque clic est un fait
-- enregistre cote serveur, jamais declare par un client.

-- 1. L'OFFRE -------------------------------------------------------------

CREATE TABLE etablissements (
  id            SERIAL PRIMARY KEY,
  slug          TEXT UNIQUE NOT NULL,
  nom           TEXT NOT NULL,
  categorie     TEXT NOT NULL CHECK (categorie IN ('restaurant', 'meuble')),
  quartier      TEXT NOT NULL,
  prix_affiche  INT NOT NULL,                  -- en FCFA, affiche AVANT le clic
  devisee       TEXT NOT NULL,                 -- "Plat du jour", "par nuit"
  photo_url     TEXT,
  whatsapp      TEXT NOT NULL,                 -- numero du commerce
  ref_code      TEXT UNIQUE NOT NULL,          -- EST-042-A7, filtre anti-declaration
  actif         BOOLEAN NOT NULL DEFAULT true, -- l'abonnement : visible ou non
  cree_le       TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_etablissements_categorie
  ON etablissements (categorie, quartier) WHERE actif;

-- 2. LA PREUVE DU CLIC ----------------------------------------------------
-- Cette table est le coeur technique du projet.
-- Elle est ecrite par le serveur, jamais par le client. Un clic est un fait.

CREATE TABLE clics (
  id            BIGSERIAL PRIMARY KEY,
  etablissement_id INT NOT NULL REFERENCES etablissements(id),
  token         TEXT UNIQUE NOT NULL,          -- voyage dans le lien et dans wa.me
  ip_hash       TEXT NOT NULL,                 -- jamais l'IP en clair : hachee avec du sel
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  compte        BOOLEAN NOT NULL DEFAULT true, -- false si doublon detecte
  motif_exclu   TEXT                            -- NULL si compte, sinon le motif
);

CREATE INDEX idx_clics_eta_date ON clics (etablissement_id, created_at DESC);

-- Anti-fraude : un seul clic par etablissement, par jour, par visiteur.
-- Cette contrainte est le vrai rempart, pas le code applicatif.
CREATE UNIQUE INDEX idx_clics_anti_fraude
  ON clics (etablissement_id, ip_hash,
            (created_at AT TIME ZONE 'Africa/Douala')::date)
  WHERE compte = true;

-- 3. LES CONVERSATIONS ----------------------------------------------------
-- Ce que le client declare avoir recu, filtre par code de reference.
-- On ne compte JAMAIS une conversation sans code : garde-fou numero 1.

CREATE TABLE conversations (
  id              BIGSERIAL PRIMARY KEY,
  etablissement_id INT NOT NULL REFERENCES etablissements(id),
  clic_id          BIGINT REFERENCES clics(id) ON DELETE SET NULL,
  ref_code         TEXT NOT NULL DEFAULT '',
  declaree_par    INT NOT NULL DEFAULT 0,      -- total annonce par le client
  date_declaration TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_conv_eta_date
  ON conversations (etablissement_id, date_declaration DESC);

-- 4. LA CHAINE DE MESURE (vue) --------------------------------------------
-- Le tableau de bord affiche cette vue, jamais un chiffre isole.
-- C'est ce qui transforme le client en controleur qualite : il voit les 4 etapes.

CREATE OR REPLACE VIEW chaine_mesure AS
SELECT
  e.id,
  e.nom,
  e.slug,
  e.ref_code,
  COALESCE(c.clics_envoyes, 0)      AS clics_envoyes,
  COALESCE(c.clics_comptes, 0)      AS clics_comptes,
  COALESCE(v.declarees, 0)          AS conversations_declarees,
  COALESCE(v.verifiees, 0)          AS conversations_verifiees,
  c.derniere_activite
FROM etablissements e
LEFT JOIN (
  SELECT etablissement_id,
         COUNT(*)                        AS clics_envoyes,
         COUNT(*) FILTER (WHERE compte)  AS clics_comptes,
         MAX(created_at)                 AS derniere_activite
  FROM clics GROUP BY etablissement_id
) c ON c.etablissement_id = e.id
LEFT JOIN (
  SELECT etablissement_id,
         MAX(declaree_par) AS declarees,
         -- Verifiee seulement si elle porte le code.
         COUNT(*) FILTER (WHERE ref_code <> '') AS verifiees
  FROM conversations GROUP BY etablissement_id
) v ON v.etablissement_id = e.id
WHERE e.actif;

Deux détails qui méritent une explication

Le fuseau horaire dans l'index. AT TIME ZONE 'Africa/Douala' fait que la journée de l'anti-fraude commence à minuit au Cameroun. Sans cela, un serveur configure en heure de Paris donnerait un décalage de plusieurs heures sur le regroupement quotidien, et le garde-fou compterait faux.

La vue fait le travail à la place du code. Compter des conversations vérifiées est une règle de gestion, pas une règle technique. En la mettant dans une vue SQL, tu n'écris pas cette logique dans trois endroits différents, et le tableau de bord ne peut pas diverger de la base.

PARTIE 3 — LE BACK-END
backend/src/db.ts Rôle : c'est le fichier le plus important du back-end. Il contient enregistrerClic, la fonction qui transforme un clic en preuve horodatée. Tout le reste n'est que de l'affichage. 
// Le serveur qui enregistre les clics. C'est le seul fichier vraiment
// important du back-end : tout le reste n'est que de l'affichage.
//
// Principe : un clic est un FAIT. Il est ecrit ici, par le serveur, horodate.
// Aucun client ne peut declarer un clic qu'il n'a pas fait.

import { Pool } from 'pg';
import crypto from 'node:crypto';

// Le sel du hachage. En production : une variable d'environnement.
// Il sert a ne jamais stocker d'IP en clair.
const SALT = process.env.CLICK_SALT ?? 'sel-de-developpement';

const pool = new Pool({
  connectionString: process.env.DATABASE_URL ??
    'postgres://plateforme:plateforme@localhost:5432/plateforme',
});

export { pool };

// Un token court et unique, qui voyage dans le lien et dans wa.me.
// 8 caracteres en base64url : illisible, mais court pour un lien WhatsApp.
function nouveauToken(): string {
  return crypto.randomBytes(6).toString('base64url');
}

// On ne veut pas l'IP en clair : personne ne doit pouvoir remonter
// a un particulier depuis la base. Le sel empeche les inversions par table.
function hacherIp(ip: string): string {
  return crypto
    .createHash('sha256')
    .update(SALT + ip)
    .digest('hex')
    .slice(0, 32);
}

export async function trouverParSlug(slug: string) {
  const { rows } = await pool.query(
    `SELECT * FROM etablissements WHERE slug = $1 AND actif`,
    [slug],
  );
  return rows[0] ?? null;
}

// Catalogue : ce que voit le visiteur. Pas de pagination
// tant qu'on n'a pas plus de 200 etablissements.
export async function listerEtablissements(categorie?: string) {
  const { rows } = await pool.query(
    `SELECT id, slug, nom, categorie, quartier, prix_affiche,
            devisee, photo_url
     FROM etablissements
     WHERE actif AND ($1::text IS NULL OR categorie = $1)
     ORDER BY quartier, nom`,
    [categorie ?? null],
  );
  return rows;
}

// LE clic. Cette fonction est le coeur du projet.
//
// Elle fait trois choses dans cet ordre :
//   1. elle cree le token et enregistre le clic ;
//   2. elle verifie si ce clic compte (anti-fraude) ;
//   3. elle renvoie l'URL WhatsApp a ouvrir.
//
// Point important : on enregistre TOUJOURS, meme un clic comptabilise comme
// frauduleux. Le journal doit etre complet pour etre auditable. C'est le champ
// `compte` qui dit si on le facture, pas la presence de la ligne.
export async function enregistrerClic(
  etablissementId: number,
  ip: string,
) {
  const token = nouveauToken();
  const ipHash = hacherIp(ip);

  // On tente l'insertion. Si l'index unique anti-fraude la refuse,
  // c'est un doublon : on garde quand meme la ligne, mais non comptabilisee.
  try {
    await pool.query(
      `INSERT INTO clics (etablissement_id, token, ip_hash)
       VALUES ($1, $2, $3)`,
      [etablissementId, token, ipHash],
    );
  } catch (err: any) {
    // violation de la contrainte unique = doublon sur la journee
    if (err?.code === '23505') {
      await pool.query(
        `INSERT INTO clics (etablissement_id, token, ip_hash,
                           compte, motif_exclu)
         VALUES ($1, $2, $3, false, 'doublon-jour')`,
        [etablissementId, token, ipHash],
      );
    } else {
      throw err;
    }
  }

  return token;
}

// La chaine affichee au client. Les 4 etapes, jamais un chiffre seul.
export async function chaineMesure(etablissementId: number) {
  const { rows } = await pool.query(
    `SELECT * FROM chaine_mesure WHERE id = $1`,
    [etablissementId],
  );
  return rows[0] ?? null;
}

// Declaration du client : combien de conversations il a recues sur SON WhatsApp.
// Rappel : cette donnee est declaree, pas verifiee.
export async function declarerConversations(
  etablissementId: number,
  nombre: number,
  refCode: string,
) {
  const { rows } = await pool.query(
    `INSERT INTO conversations (etablissement_id, declaree_par, ref_code)
     VALUES ($1, $2, $3) RETURNING *`,
    [etablissementId, nombre, refCode],
  );
  return rows[0];
}

Pourquoi on enregistre quand même un clic frauduleux ? Parce que le journal doit être complet pour être auditable. Si tu effaces les doublons, tu ne peux plus prouver à un client qui a triché que tu as détecté sa tentative. La ligne est conservée, le champ compte passe à faux, et le motif est écrit : doublon-jour.

Le hachage de l'IP

On ne conserve jamais une adresse IP en clair. Une IP est une donnée personnelle : elle localise une personne. Le hachage avec un sel empêche de remonter d'un haché vers l'adresse d'origine, y compris par table de correspondance. Le sel vit dans une variable d'environnement, donc il ne voyage pas dans le dépôt.

backend/src/server.ts Rôle : les quatre routes HTTP. La deuxième est la plus importante du projet — c'est elle qui enregistre le clic et redirige vers WhatsApp. 
// Le serveur HTTP. Quatre routes seulement :
//   GET  /api/etablissements          le catalogue
//   GET  /c/:slug                     le clic : enregistre, puis redirige
//   GET  /api/et/:id/tableau           la chaine de mesure
//   POST /api/et/:id/declaration       ce que le client declare avoir recu

import Fastify from 'fastify';
import cors from '@fastify/cors';
import {
  trouverParSlug,
  listerEtablissements,
  enregistrerClic,
  chaineMesure,
  declarerConversations,
} from './db.js';

const app = Fastify({ logger: true });

// L'API est appelee par le front Next.js, donc on autorise les appels locaux.
// En production, restreindre `origin` aux domaines reels.
app.register(cors, { origin: true });

// --- 1. Le catalogue public -----------------------------------------------

app.get('/api/etablissements', async (req) => {
  const { categorie } = req.query as { categorie?: string };
  return { etablissements: await listerEtablissements(categorie) };
});

// --- 2. LA ROUTE DU CLIC ---------------------------------------------------
// C'est la route qui fait vivre le projet. Elle est volontairement separate :
// elle ne rend rien, elle enregistre et redirige. Aucun JavaScript.
//
// Le ref_code voyage dans l'URL WhatsApp pour que l'utilisateur puisse le
// renvoyer dans son message. C'est le seul moyen, depuis un numero tiers,
// d'avoir une trace que la conversation a eu lieu.

app.get('/c/:slug', async (req, reply) => {
  const { slug } = req.params as { slug: string };

  const etablissement = await trouverParSlug(slug);
  if (!etablissement) {
    return reply.code(404).send({ erreur: 'etablissement inconnu' });
  }

  const ip = req.ip;
  const token = await enregistrerClic(etablissement.id, ip);

  // WhatsApp ouvre la discussion chez le commerce, pas chez nous.
  const texte = encodeURIComponent(
    `Bonjour, je viens de votre page (ref ${etablissement.ref_code}).`,
  );
  const urlWa = `https://wa.me/${etablissement.whatsapp}?text=${texte}`;

  reply.header('Set-Cookie',
    `clic=${token}; Path=/; Max-Age=86400; SameSite=Lax`);

  // 302 : temporaire. On veut que le lien soit rejouable.
  return reply.redirect(urlWa, 302);
});

// --- 3. La chaine de mesure ------------------------------------------------

app.get('/api/et/:id/tableau', async (req) => {
  const { id } = req.params as { id: string };
  return await chaineMesure(Number(id));
});

// --- 4. La declaration du client ------------------------------------------
// Le client dit combien il a recu. On ne le croit pas : on enregistre,
// et la vue ne compte comme verifie que ce qui porte le code.

app.post('/api/et/:id/declaration', async (req, reply) => {
  const { id } = req.params as { id: string };
  const { nombre, refCode } =
    req.body as { nombre?: number; refCode?: string };

  if (typeof nombre !== 'number' || nombre < 0) {
    return reply.code(400).send({ erreur: 'nombre invalide' });
  }

  // Garde-fou : on ne compte jamais plus que les clics envoyes.
  const chaine = await chaineMesure(Number(id));
  const plafond = chaine?.clics_envoyes ?? 0;

  return reply.send({
    enregistrement: 'ok',
    valeur_annoncee: nombre,
    clics_envoyes: plafond,
    plafond_a: Math.min(nombre, plafond),
    remarque:
      nombre > plafond
        ? 'Valeur superieure au nombre de clics envoyes : impossible.'
        : null,
  });
});

const port = Number(process.env.PORT ?? 3001);
await app.listen({ port, host: '0.0.0.0' });

Trois détails qui font la différence

Aucun JavaScript sur la route du clic. La route /c/:slug enregistre puis renvoie une redirection HTTP 302. Un clic mesuré en JavaScript peut être bloqué par un bloqueur de publicités, par une extension, ou par un navigateur qui l'interprète mal. Une redirection serveur ne peut pas échouer.

Le statut 302, pas 301. Une redirection permanente serait mémorisée par le navigateur et le lien ne fonctionnerait qu'une seule fois. Ici le lien reste rejouable, ce qui est nécessaire quand un utilisateur revient sur la fiche.

Le code de référence voyage dans le message. Le message pré-rempli contient ref EST-042-A7. C'est la seule trace possible depuis un numéro tiers : si l'utilisateur renvoie ce code dans son message, on sait que la conversation a eu lieu. Ce n'est pas une preuve, c'est un filtre — et il suffit à rendre la fraude inutile quand on ne paie jamais à l'unité.

import Link from 'next/link';

const API = process.env.API_URL ?? 'http://localhost:3001';

export type Etablissement = {
  id: number;
  slug: string;
  nom: string;
  categorie: 'restaurant' | 'meuble';
  quartier: string;
  prix_affiche: number;
  devisee: string;
  photo_url: string | null;
};

async function getCatalogue(
  categorie?: string,
): Promise<Etablissement[]> {
  const url =
    categorie && categorie !== 'tout'
      ? `${API}/api/etablissements?categorie=${categorie}`
      : `${API}/api/etablissements`;

  // revalidate : le catalogue change peu, on ne veut pas requeter l'API
  // a chaque visite. 60 secondes suffisent.
  const res = await fetch(url, { next: { revalidate: 60 } });
  if (!res.ok) return [];
  const data = await res.json();
  return data.etablissements ?? [];
}

Deux décisions valent une explication. D'abord next: { revalidate: 60 } : le catalogue bouge peu, et re-requêter l'API à chaque visite poserait un problème de latence inutile. frontend/app/e/[slug]/page.tsx Rôle : la fiche d'un établissement, et surtout le bouton. Le bouton ne pointe pas vers WhatsApp — il pointe vers notre route /c/:slug. C'est le point le plus important du front-end. 
// La fiche d'un etablissement.
//
// Le bouton « Decouvrir plus » ne pointe PAS vers WhatsApp directement.
// Il pointe vers notre route /c/:slug, qui enregistre le clic (serveur)
// et redirige ensuite vers WhatsApp.
//
// C'est le point le plus important de tout le front-end.
// Si on mettait wa.me directement dans le href, on n'aurait aucune mesure.

import Link from 'next/link';
import { notFound } from 'next/navigation';

const API = process.env.API_URL ?? 'http://localhost:3001';

type Etablissement = {
  id: number;
  slug: string;
  nom: string;
  categorie: string;
  quartier: string;
  prix_affiche: number;
  devisee: string;
  photo_url: string | null;
  whatsapp: string;
  ref_code: string;
};

function fcfa(n: number): string {
  return `${n.toLocaleString('fr-FR').replace(/\u202f|\u00a0/g, ' ')} FCFA`;
}

export default async function Fiche({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;

  const res = await fetch(`${API}/api/etablissements`, {
    next: { revalidate: 60 },
  });
  const tous: Etablissement[] = (await res.json()).etablissements ?? [];
  const etablissement = tous.find((e) => e.slug === slug);

  if (!etablissement) notFound();

  return (

      <article>
        <h1>{etablissement.nom}</h1>
        <p className="quartier">{etablissement.quartier}</p>

        <p className="prix">
          <strong>{fcfa(etablissement.prix_affiche)}</strong>
          <span>{etablissement.devisee}</span>
        </p>

        {/* LE point central : on passe par /c/:slug, pas par wa.me. */}

           href={`http://localhost:3001/c/${etablissement.slug}`}>
          Decouvrir plus sur WhatsApp
        </a>

        {/* Transparence : le client sait que son clic sera compte.
            La transparence est une contre-mesure anti-fraude. */}
        <p className="mention">
          Votre clic est enregistre. Vous engagez la conversation
          directement avec l'etablissement, sur son numero WhatsApp.
        </p>
      </article>

      <Link href="/">Retour au catalogue</Link>
    </main>
  );

Le piège à éviter absolument : mettre https://wa.me/23769... directement dans le href. Le clic part, WhatsApp s'ouvre, et il n'existe aucune trace côté serveur. Un clic non mesuré est un clic invendable : tu ne peux ni le facturer, ni prouver au client qu'il a eu lieu.

// Le tableau de bord du client.

const API = process.env.API_URL ?? 'http://localhost:3001';

  nom: string;
  slug: string;
  ref_code: string;

  clics_comptes: number;

  conversations_verifiees: number;
  derniere_activite: string | null;

              <td>{chaine.conversations_declarees}</td>
            </tr>

PARTIE 5 — MONTAGE PAS À PAS

5. Lancer l'application en une commande

Un script est fourni à la racine du dossier : ./demarrer.sh. Il vérifie les prérequis, démarre la base, crée le schéma seulement s'il est absent, insère les données, puis lance le back-end et le front-end en arrière-plan.

# Tout lancer
./demarrer.sh

# Tout arreter
./demarrer.sh arret

# Suivre les journaux
tail -f /tmp/back.log
tail -f /tmp/front.log

Le script est volontairement idempotent : le relancer ne réinitialise pas la base et ne duplique pas les établissements. C'est utile pendant une journée de développement où on relance souvent.

L'erreur la plus probable au premier lancement est que Docker soit installé mais arrêté. Le script la détecte et affiche la commande selon ton système :

Sur Linux    : sudo systemctl start docker
Sur Mac      : ouvre Docker Desktop, attends le logo
Sur Windows  : ouvre Docker Desktop, attends le logo

Pour verifier :  docker info

Sans ce démon, rien ne démarre, et aucune base de données n'est disponible.

11. État de vérification de ce code

Ce qui a été vérifié : les deux projets compilent sans erreur TypeScript (tsc --noEmit passe sur le back-end et le front-end), le serveur Fastify démarre et répond, le script demarrer.sh a une syntaxe bash valide, et le fichier docker-compose.yml est accepté par docker compose config.

Trois défauts ont été trouvés et corrigés pendant cette vérification : le chemin du schéma était faux dans le script initdb, next-env.d.ts manquait, et l'API catalogue ne renvoyait pas d'identifiant, ce qui cassait le tableau de bord.

Ce qui n'a pas pu être vérifié : l'exécution complète avec la base de données. Le démon Docker ne tourne pas sur la machine où ce code a été écrit, et il exige les privilèges root pour démarrer. Les commandes des sections 5 et 7 n'ont donc pas été exécutées de bout en bout : elles restent à confirmer chez toi.

Concrètement, ce qui reste non testé : la création effective des tables, le seed, la redirection 302 vers wa.me, et le refus du doublon par l'index unique. Le code de ces chemins est relu et typé, mais pas exécuté.

13. La règle de séquencement

Ces cinq éléments de base peuvent démarrer maintenant, sans attendre la validation du prix de vente.
